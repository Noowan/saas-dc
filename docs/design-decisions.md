
# Design decisions

## Underlay и ASN

Каждый leaf имеет два независимых eBGP-соседа, ECMP достигается за счёт равной стоимости `/31` маршрутов до loopback VTEP. В FRR используется глобальный ASN 65000 для единого процесса и iBGP EVPN overlay, а на underlay neighbors заданы per-neighbor `local-as`/`remote-as`: leaf-1..7 используют 65101..65107, spine-1/2 — 65001/65002. Это позволяет одновременно сохранить требование eBGP underlay и iBGP overlay.

## EVPN control-plane

Spine-1 и spine-2 — route-reflector для l2vpn evpn. Leaf устанавливает iBGP EVPN-сессии по loopback с обоими spine. Data-plane — VXLAN UDP/4789. Type-2, Type-3 и Type-5 включены явно: первые два обеспечивают L2 stretch/BUM, Type-5 — обмен префиксами в VRF для symmetric IRB.

## RD и RT

RD уникален на VTEP и VNI: `<vtep-loopback>:<vni>`. RT намеренно одинаков для одного клиенсткого VNI на всех leaf, чтобы маршруты импортировались всеми VTEP с этим VRF. VRF vrf-CLIENT_A и vrf-CLIENT_B используют непересекающиеся RT и L3 VNI, поэтому одинаковые подсети не смешиваются и клиенты изолированы друг от друга.

## Anycast Gateway и symmetric IRB, MAC адреса для anycast gateway

Все VTEP, имеют одинаковый IP на каждом SVI и virtual MAC. L3 VNI используется как транзит для VRF . При локальном east-west трафике пакет маршрутизируется на ingress leaf, инкапсулируется в L3 VNI и распаковывается на egress leaf; это symmetric IRB. Мак адреса для VNI разные т.к. мне так захотелось, можно одинаковый везде, в таблице EVPN они будут разделяться RT и никогда не пересекутся.

## EVPN Multihoming All-Active

`cl-b-vni20202-mh` использует LACP 802.3ad к leaf-1/leaf-2. На обоих leaf одинаковый es-id 20202 и es-sys-mac 02:00:00:02:02:02. DF election для BUM выполняется EVPN MH control-plane. При желании можно выставить приоритет и самому определить DF. Команда evpn mh es-df-pref на bond интерфейсе leaf-1 или leaf-2

## MLAG против EVPN MH

EVPN MH предпочтительнее, потому что он не требует отдельного вендорозависимого протокола между leaf и хорошо масштабируется. MLAG пусть будет для каких-нибудь специфических устройств, которые не могут работать с EVPN MH, например из-за отсутствия возможности работать в All-Active режиме. Leaf-3/leaf-4 имеют peer-link, общий L2 forwarding domain и подключенный к ним обоим хост. Пришлось сделать на Arista EOS т.к. FRR не умеет в MLAG.

## Border/Gateway

Edge-leaf 5 подключён к роутеру internet отдельным eBGP линком. Internet объявляет default route. Egde-leaf5 принимает default и экспортирует его в VRF для клиента А и Б также делает из обычного ipv4 маршруты EVPN Type-5 маршрут.
За internet стоит хост, который эмулирует 8.8.8.8 и можно проверить связность с любой машины клиента. Для того, чтобы выйти в "интернет" используется NAT на egde-leaf5. Для этого пришлось пересобрать образ FRR, добавив в него iptables и iproute2. При запуске лабы важно подготовить этот образ с помощью deploy.sh или самостоятельно сделать docker build с tag lab/frr-edge:nat. Скрипт в exec edge-leaf-5 для NAT для клиентов мне помог написать интернет. Я не сильно силен в таких штуках в Linux, но я так понял, что там создается 2 namespace для двух VRF, 2 veth интерфейса, как будто 2 кабеля для каждого namespace и дальше через macvlan интерфейс, где 2 адреса с отдельными маками всё это маршрутизируется либо во внешний интерфейс, либо в VRF.
Внизу к скрипту на всякий случай добавил анонс 8.8.8.8/32 по аналогии с default. Можно убрать, все будет ходить по default.

## QoS

Реализована QoS на базе утилиты tc в linux. Конфигурация разделена на два основных этапа: классификация (маркировка) входящего клиентского трафика и управление полосой пропускания (шейпинг) на аплинках.

##### 1. Маркировка входящего клиентского трафика
Для приоритизации пакетов на входящих интерфейсах (ingress) активирована дисциплина обработки очередей clsact. Модификация полей IP-пакетов выполняется с помощью утилиты pedit с последующим пересчетом контрольной суммы (csum):
• Интерфейсы eth5 (Приоритетный клиент): Весь входящий трафик маркируется кодом EF (Expedited Forwarding). Для этого в поле DSCP записывается значение 0xb8 (маска сохранения 0xfc).
• Интерфейсы eth3 и eth4 (Обычные клиенты): Весь входящий трафик сбрасывается в класс BE (Best Effort) путем принудительной установки значения DSCP в 0x00.
Таким образом клиентскому DSCP мы не доверяем!

##### 2. Управление очередями и полосой пропускания на аплинках (eth1 и eth2)
На исходящих интерфейсах eth1 и eth2 настроена идентичная иерархическая структура классов на базе алгоритма HTB с ограничением максимальной пропускной способности канала в 100 Мбит/с (ceil 100mbit). Так удобнее тестировать в containerlab.
Выделено три класса обслуживания с гарантированной скоростью и приоритетом:

| Идентификатор класса |	Класс QoS	Гарантированная скорость (rate) |	Макс. скорость (ceil)	| Приоритет (prio) |	Алгоритм честной очереди |
|---|---|---|---|---|
| 1:10 |	CS6 + CS7  (служебный трафик)	 5 Мбит/с	 | 100 Мбит/с если другие не заняты	|0 (Наивысший)|	fq_codel |
| 1:20 |	EF (приоритетный сегмент)	25 Мбит/с |	100 Мбит/с |	1 (Высокий) |	fq_codel |
| 1:30 |	BE (Остальной трафик / По умолчанию)	70 Мбит/с |	100 Мбит/с |	2 (Низкий) |	fq_codel |



##### 3. Фильтрация и распределение трафика по классам
Распределение пакетов по созданным HTB-классам на аплинках осуществляется с помощью фильтра u32, который анализирует поле dsfield (DSCP) с маской 0xfc:
• Трафик с маркерами CS6 (0xc0) и CS7 (0xe0) направляется в высокоприоритетный класс 1:10 для минимизации задержек управляющих пакетов.
• Трафик с маркером EF (0xb8), приходящий от клиента на eth5, попадает в класс 1:20.
• Весь остальной неклассифицированный трафик (включая BE с интерфейсов eth3 и eth4) автоматически обрабатывается классом по умолчанию 1:30 (default 30).


## EVPN route types
- Type-1: Ethernet Auto-Discovery для быстрой сходимости и для объявления доступности ES через VTEPы.
- Type-2: MAC/IP advertisements для host MAC/IP и Anycast SVI.
- Type-3: IMET routes для VXLAN BUM replication.
- Type-5: IP prefix advertisements из VRF для symmetric IRB/L3 stretch.
- Type-4: Ethernet Segment route для выбора DF и поиска пиров при EVPN MH
Spines не являются VTEP: они только route-reflector для EVPN и маршрутизируют underlay. VTEP source — loopback leaf.

## QoS и MTU

Транзитные интерфейсы выставляются в MTU 9216, VXLAN-интерфейсы — 9000. Low-latency workload маркирует DSCP EF (`46`) и IEEE 802.1p/CoS 5. `qos.sh` создаёт 4 класса `tc mqprio` и фильтр flower для DSCP EF/CS5. В production настройки очередей и ECN должны быть согласованы с ASIC buffer profile и DCB policy.
